## 작업 내용

사용자는 평소에도 비밀번호를 바꿀 수 있고, 임시 비밀번호로 로그인한 직후에는 반드시 바꿔야 한다.

### 범위
- [x] 비밀번호 변경 API: 평소에는 현재 비밀번호와 새 비밀번호, 강제 변경(임시 비밀번호 직후)에는 새 비밀번호만
- [x] 새 비밀번호는 8자 이상
- [x] 변경하면 비밀번호 변경 시각이 갱신되어 이전 토큰이 모두 무효

제외: 비밀번호 찾기(셀프 초기화)

### 완료 조건
- [x] 평소 변경과 강제 변경이 각각 동작한다.
- [x] 변경 후 이전 토큰이 거부된다.
- [x] 강제 변경이 끝나면 임시 비밀번호 상태가 해제된다.

### 결정 필요
- [x] 변경 직후 로그인 상태가 유지되도록 응답으로 새 토큰을 줄지, 다시 로그인하게 할지: **새 토큰을 준다.** `docs/api/openapi.yaml`(`ChangePasswordResponse`)이 이미 이렇게 정해 두어 그대로 따른다.

## 설계 (Claude가 정함)
- 규격 `POST /api/v1/auth/password` 그대로: 요청 `{currentPassword?, newPassword}`, 응답 `{accessToken}`. 의존성은 #16의 `current_account_for_password_change`(임시 비밀번호 상태를 통과시키고, 차단과 낡은 토큰은 그대로 거부).
- 규칙: 관리자 계정은 403 `FORBIDDEN`(설정으로만 변경). 임시 비밀번호 상태가 아니면 `currentPassword` 필수(없으면 422 `VALIDATION_FAILED`, 틀리면 401 `INVALID_CREDENTIALS`). 임시 비밀번호 상태에서는 `currentPassword`를 무시한다.
- 변경하면 `password_hash`, `password_changed_at`을 갱신하고 `password_change_required`를 false로 한다. 새 토큰은 변경 시각 **이후**에 발급한다(같은 시각이면 비교가 위험).
- 비밀번호 상한 1024자(로그인 `password`, 변경 `currentPassword`/`newPassword`). #15 리뷰에서 "요청 크기 제한은 #17에서"로 넘긴 항목이다. 이슈에 없던 결정이라 규격에 먼저 반영했다.
- 규격 보완: 이 API의 401(토큰 문제 `UNAUTHORIZED` 또는 현재 비밀번호 오류 `INVALID_CREDENTIALS`)과 403(관리자 `FORBIDDEN` 또는 차단 `ACCOUNT_BLOCKED`)이 각각 두 종류인데 규격에는 하나씩만 있어 둘 다 적었다.
- 새 비밀번호는 지금 비밀번호(임시 비밀번호 포함)와 달라야 한다(같으면 422 `VALIDATION_FAILED`). 이슈 배경이 "임시 비밀번호 직후에는 **반드시 바꿔야 한다**"이고, 관리자가 아는 임시 비밀번호를 그대로 쓰면 변경이 아니기 때문이다. 이슈에 없던 결정이라 규격에 먼저 반영했다. 빈 문자열 `currentPassword`는 없는 것과 같이 422로 처리한다.
- 같은 계정의 동시 변경은 행 잠금(`SELECT ... FOR UPDATE`)으로 순서대로 처리한다. 잠근 뒤 다시 읽어서 먼저 끝난 변경을 반영한 값으로 검사하므로 하나만 성공하고 나머지는 401이다.
- argon2 재해시(`check_needs_rehash`)는 이번에도 만들지 않는다. 해시 파라미터를 바꾸는 때 로그인과 함께 구현한다(지금은 바꿀 일이 없고, 비밀번호를 바꾸면 현재 파라미터로 새로 해시된다).

- 수정: `backend/app/{auth,security,errors}.py`, `backend/tests/test_security.py`, `backend/CLAUDE.md`, `docs/api/openapi.yaml`

### 확인 방법과 결과
- 테스트: `cd backend && uv run pytest` → 134 passed(리뷰 반영 후, 비밀번호 변경 API 테스트 23개 포함, 실제 `iris_test` DB와 앱 시작까지 실행).
- **평소 변경과 강제 변경이 각각 동작**: 평소에는 현재+새 비밀번호로 200과 새 토큰, 현재 비밀번호 없음 422, 틀림 401(아무것도 바뀌지 않음). 강제 변경은 새 비밀번호만으로 200이고, 임시 비밀번호로 보낸 `currentPassword`는 무시.
- **변경 후 이전 토큰이 거부됨**: 같은 계정의 토큰 2개 모두 401, 옛 비밀번호 로그인 401, 새 비밀번호 로그인 200, `password_changed_at`이 이전보다 늦고 해시는 argon2이며 새 비밀번호로 검증됨. 변경 직후 받은 새 토큰이 같은 시각 비교로 거부되는지 5회 연속 변경으로 확인.
- **강제 변경이 끝나면 임시 비밀번호 상태 해제**: DB의 `password_change_required`가 false, 재로그인 응답의 `passwordChangeRequired`가 false, 변경 전에 403이던 일반 경로가 200.
- 그 밖: 새 비밀번호 0자·7자·1025자 → 422(아무것도 바뀌지 않음), 1024자는 통과하고 그 비밀번호로 로그인됨, 로그인과 변경의 1025자 비밀번호는 422, 관리자는 403 `FORBIDDEN`(비밀번호 그대로), 차단된 계정은 403 `ACCOUNT_BLOCKED`, 토큰 없음·쓰레기 토큰은 401 `UNAUTHORIZED`.
- **변이 검사**: 현재 비밀번호 검증 제거, 비밀번호 변경 시각 갱신 제거, 임시 비밀번호 상태 해제 제거, 관리자 차단 제거, 저장(commit) 제거, 임시 비밀번호 상태에서도 현재 비밀번호 요구를 각각 적용해 테스트가 실패하는지 확인한 뒤 원복했다. 6개 모두 잡혔다.
- **실제 서버(개발 DB)**: 임시 계정으로 임시 비밀번호 로그인(`passwordChangeRequired` true) → 7자 미만 422 → 강제 변경 200 → 옛 토큰 401 → 새 비밀번호 로그인(`passwordChangeRequired` false) → 평소 변경에서 현재 비밀번호 없음 422, 틀림 401, 성공 200 → 평소 변경 뒤 옛 토큰 401, 관리자 403. 서버 로그에 오류 0건. 확인 후 임시 계정 삭제, 개발 DB에는 `admin`만 남음.
- 규격: `npx --yes @redocly/cli@1.34.5 lint docs/api/openapi.yaml` → valid(경고 2건은 이전과 같은 의도한 값).
- **동시 변경(리뷰 반영 후)**: 같은 계정에 두 요청을 동시에 보내면 하나만 성공(200)하고 하나는 401이며, 성공한 쪽의 토큰이 바로 쓸 수 있음을 테스트. 행 잠금을 빼면 3번 모두 실패(둘 다 성공)하고, 잠금이 있으면 20번 연속 통과.
- 확인하지 못한 것: 서로 다른 프로세스(워커 여러 개)에서의 동시 변경(행 잠금은 DB에서 걸리므로 같은 결과일 것이나 시험하지 않음).

### 코드 리뷰 반영 내역
지적 8건 중 5건 반영, 3건 넘어감.
- 반영(진짜 경쟁 조건): 같은 계정의 동시 변경. 테스트로 재현(둘 다 성공)한 뒤 행 잠금으로 해결
- 반영: 새 비밀번호가 현재·임시 비밀번호와 같으면 422. 이슈 배경("반드시 바꿔야 한다")에 근거한 이슈 밖 결정이라 규격과 PR에 적음
- 반영: 빈 문자열 `currentPassword`를 없는 것과 같이 422로 처리
- 반영: 테스트 빈틈 보강(변경 API에서의 낡은 토큰, 강제 변경 상태의 관리자·차단 계정, 동시성). 앞의 3개는 이미 통과하던 규칙의 빈틈이었음
- 반영: 이 작업 파일의 상태, 결과, 리뷰 내역 갱신
- 넘어감: 토큰을 훔친 쪽이 이 API로 현재 비밀번호를 추측하는 문제. 로그인과 같은 "시도 횟수 제한 없음" 빈틈으로 기록되어 있고 별도 이슈 대상
- 넘어감: argon2 동안 DB 연결 점유. 동시 변경을 막는 행 잠금을 쥔 채 검증해야 해서 의도한 설계이고, 인증된 사용자만 호출할 수 있음
- 넘어감: `iat` 부동소수 반올림으로 새 토큰이 낡은 것으로 보일 수 있다는 지적. 변경 흐름은 저장한 뒤 수 ms 이상 지나 토큰을 발급하고 로그인 토큰은 훨씬 뒤라 실제로 닿을 수 없는 경계
