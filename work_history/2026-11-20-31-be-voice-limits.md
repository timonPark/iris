## 작업 내용

whisper와 claude 보정은 PC 자원을 많이 쓰므로 음성 처리는 동시 1건으로 제한하고, 나머지는 거절하지 않고 순서대로 대기시킨다. 음성 파일은 성공이든 실패든 처리가 끝나면 남지 않게 한다.

### 범위
- [x] 음성 처리는 동시 1건, 나머지는 거절하지 않고 들어온 순서대로 대기
- [x] 변환이 끝나면(성공이든 실패든) 음성 파일 삭제 보장

제외: 동시 처리 수 확대

### 완료 조건
- [x] 처리 후(실패 포함) 음성 파일이 남아 있지 않다.
- [x] 동시에 여러 건을 보내면 한 건씩 순서대로 처리된다.

### 결정 필요 (Claude가 정함)
- **대기 상한**: 순서를 기다리는 시간이 120초를 넘으면 그 요청은 500 `VOICE_PROCESSING_FAILED`("다시 시도해 주세요")로 끝낸다. 새 오류 코드를 만들지 않고 규격의 500 설명에 이 경우를 보탠다. 대기 인원 수에는 상한을 두지 않는다(계정은 관리자가 등록하는 소수라서).
- **앱에 대기 중임을 보여주는 방식**: 별도 이벤트를 만들지 않는다. 응답은 처리가 끝난 뒤에 시작하는 SSE이고 오류는 HTTP 상태로 돌려주는 계약을 그대로 두며, 앱은 요청이 진행되는 동안 "처리 중"을 보여준다(대기와 처리를 구분하지 않음).

## 설계
- 대기열은 `VoiceQueue`(동시 1건의 세마포어, 들어온 순서대로 풀림)이고 `app.state.voice_queue`에 둔다. 서버 프로세스가 하나일 때만 정확하다(#23의 작업 등록부와 같은 전제).
- 순서를 얻은 뒤에 녹음을 임시 폴더로 옮기고 처리한다. 대기 중에 클라이언트가 끊겼으면 처리하지 않는다(끊긴 요청이 줄을 차지하며 whisper를 돌리지 않게).
- 파일 삭제 보장: 처리마다 임시 폴더째 지우는 것은 #30에서 했다. 서버가 강제로 꺼져서 남은 폴더는 다음 시작 때 한 시간이 지난 `iris-voice-*` 폴더를 지운다(같은 PC의 다른 서버가 처리 중인 폴더는 건드리지 않게 오래된 것만).

## 결과

### 변경한 파일
- 규격: `docs/api/openapi.yaml`(대기 방식, 120초 상한, 차례 후 세션 재확인, 500 설명)
- 코드: `backend/app/voice.py`(`VoiceQueue`, `sweep_leftover_folders`, 보정 재시도), `voice_api.py`, `main.py`
- 테스트: `tests/test_voice_queue.py`(새 파일), `test_voice_pipeline.py`, `fakes.py`(`FakeVoice` 동시 처리 수 기록)
- 문서: `backend/CLAUDE.md`

### 확인 방법과 결과
- 전체 테스트 345개 통과. 동시 4건을 보내면 모두 200이고 동시에 처리된 최대 수가 1, 들어온 순서대로 처리. 대기 상한 초과, 대기 중 끊김, 실패 후 차례 반납, 강제 종료로 남은 폴더 청소(오래된 것만)와 시작 때 청소를 각각 확인.
- 변이 검사 8가지(동시 2건 허용, 끊긴 요청 처리, 대기 상한 제거, 차례 반납 안 함, 대기 수 안 줄임, 폴더 나이 검사 제거, 대기열 안 씀, 시작 때 청소 안 함) 모두 감지.
- 실제 서버 + 실제 Hermes + 실제 도구로 동시 3건: 첫 이벤트가 4.6s, 8.5s, 12.4s로 약 4초 간격(한 건씩 순서대로), 모두 200, 임시 폴더 잔여 0, 서버 로그 오류 없음, 임시 계정 삭제 후 개발 DB에는 `admin`만 남음.
- 첫 실제 확인에서 세 번째 요청이 500이었다: 보정기가 지시형 문장("한 단어로만 답해줘")에 교정이 아니라 답을 한 것을 결과 검사가 막은 것(약 6번에 1번 발생). 검사에 걸리면 한 번만 다시 부르도록 고침(테스트 먼저). 실행 실패와 시간 초과는 다시 부르지 않음. 고친 뒤 같은 확인에서 3건 모두 200.
- 완료 조건 2개 충족: 처리 후(실패, 대기 초과, 취소 포함) 음성 파일이 남지 않음 / 동시에 보내면 한 건씩 순서대로 처리.
