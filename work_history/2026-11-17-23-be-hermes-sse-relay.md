## 작업 내용

질문을 Hermes에 전달하고 답변을 SSE로 클라이언트에 돌려준다. 맥락은 Iris DB가 기준이라서 질문마다 그 세션의 이전 질문과 답변을 함께 보낸다.

### 범위
- [x] 질문마다 그 세션의 이전 질문·답변 전체를 DB에서 꺼내 Hermes(`/v1/chat/completions` 스트림)에 함께 전달(길이 한도 규칙은 만들지 않는다)
- [x] 답변 조각을 SSE로 중계하고, 완료되면 질문과 답변을 저장(첫 질문이면 세션도 생성)
- [x] 답변 중지: 중지하면 Hermes 호출을 끊고 받은 부분까지 "중단됨"으로 저장
- [x] Hermes 호출이 실패하면 질문과 세션을 저장하지 않고 "서버 오류"만 돌려준다
- [x] 요청마다 계정 상태 확인(#16)
- [x] 옛 세션에도 질문 가능(맥락 보장은 안 함)

제외: Hermes가 하는 일(옵시디언 저장·조회 등)은 구현하지 않는다(ADR 0001).

### 완료 조건
- [x] 같은 세션에서 앞 대화를 참조한 질문에 맞게 답한다.
- [x] 중지하면 받은 부분이 "중단됨"으로 저장된다.
- [x] Hermes가 꺼져 있으면 "서버 오류"가 나가고 아무것도 저장되지 않는다.

### 결정 필요 (Claude가 정함, 사용자는 "대안을 가져와 판단하라"고 지시)
- [x] **스트리밍 도중 Hermes 오류**: 이미 받은 답변 조각이 있으면 사용자가 본 것이므로 "중단됨"으로 저장하고 `error` 이벤트를 보낸다. 받은 조각이 없으면 아무것도 저장하지 않고 `error` 이벤트만 보낸다. (이 경우 `session` 이벤트로 알려 준 ID의 세션은 만들어지지 않는다.)
- [x] **중지 방식**: 규격이 이미 정한 별도 API(`POST /sessions/{id}/stop`)로 받는다. 그리고 **클라이언트 연결이 끊긴 것은 중지가 아니다.** 모바일 앱이 백그라운드로 가서 끊겨도 서버는 Hermes 답변을 끝까지 받아 저장한다. 근거: 이슈 #10에서 "서버가 Hermes 연결을 끊으면 Hermes도 멈춘다"는 것을 확인했고 그 연결은 서버가 쥐고 있어 제어할 수 있다. 연결 끊김을 중지로 보면 휴대폰이 잠들 때마다 긴 답변이 잘린다.

## 설계 (Claude가 정함)
- **실행(run)을 요청과 분리한다.** 질문 하나의 처리는 서버 안의 비동기 작업(run)이고, SSE 응답은 그 작업이 내보내는 이벤트를 읽어서 흘려보내는 것일 뿐이다. 그래서 클라이언트가 끊겨도 작업은 계속되어 저장까지 한다. 작업은 세션당 하나만 허용(`SESSION_BUSY`, 409)하며 메모리의 등록부(`RunRegistry`)로 관리한다. **서버 프로세스가 하나일 때만 정확하다**(워커를 여러 개 쓰면 `SESSION_BUSY`와 중지가 어긋난다). 단일 PC 단일 프로세스 구성이라 이번에는 이렇게 한다.
- 첫 질문의 세션 ID는 미리 만들어 `session` 이벤트로 바로 알려 준다(중지에 필요). DB 행은 답변을 저장할 때 만들어진다(`save_exchange`의 새 세션 ID 지정).
- Hermes 호출이 **시작되기 전에** 실패하면(연결·인증 오류) SSE가 아니라 500 `SERVER_ERROR` JSON을 돌려주고 아무것도 저장하지 않는다. 이를 위해 Hermes가 스트림을 열 때까지 기다렸다가 응답을 시작한다(첫 답변 조각이 아니라 연결 성공 시점. 도구를 쓰느라 첫 조각이 늦어도 응답이 늦게 시작되지 않는다).
- Hermes가 답을 하나도 보내지 않고 끝나면 오류로 처리한다(빈 답변을 저장하면 이후 맥락에 빈 assistant 메시지가 들어가 모델 API가 거부할 수 있다).
- 받은 조각이 없을 때 사용자가 중지하면 빈 답변을 "중단됨"으로 저장한다(화면에 중단된 답변 표시). 이후 맥락에서는 빈 답변을 `(답변 없이 중단됨)`이라는 assistant 메시지로 대신한다.
- 중지 API: 같은 계정의 진행 중 작업이 있으면 멈추라고 신호하고 204(저장은 그 뒤). 없으면 내 세션이면 409 `NOT_STREAMING`, 아니면 404 `SESSION_NOT_FOUND`(남의 진행 중 작업의 존재를 알려 주지 않음).
- 답변이 오래 걸리는 동안 터널이 연결을 끊지 않도록 15초마다 `: keepalive` 주석 줄을 보낸다.
- DB 연결은 스트리밍 동안 붙잡지 않는다(앞 단계의 조회가 끝나면 반납). 저장은 작업이 자기 세션으로 한다.
- 규격에 없던 동작을 규격에 먼저 적었다(`lint` 통과): 도중 오류의 저장 규칙, 연결이 끊겨도 끝까지 저장, 빈 답변은 오류, 422의 두 종류(`QUESTION_TOO_LONG`, `VALIDATION_FAILED`), 중지의 세부.

- **같은 세션에서 앞 대화를 참조한 질문에 맞게 답한다**: 실제 Hermes로 "내 비밀 단어는 파란고래야. 기억했다고만 답해" 다음 같은 세션에서 "비밀 단어가 뭐지?"를 물으면 "파란고래"로 답함(테스트와 실제 서버 모두). 가짜 Hermes로는 Hermes가 받은 메시지 목록이 이전 질문·답변 전체 + 새 질문과 정확히 같은지, 다른 세션과 다른 사용자의 대화는 섞이지 않는지, 중단된 답변은 포함되고 빈 답변은 표시로 바뀌는지 확인.
- **중지하면 받은 부분이 "중단됨"으로 저장된다**: 중지 204 → SSE가 `stopped`로 끝남 → 받은 부분이 `stopped`로 저장됨 → 가짜 Hermes 스트림이 취소됨. 실제 Hermes로 확인: 긴 답변 도중 중지하면 48자가 `stopped`로 저장되고 Hermes의 진행 중 실행 수가 1에서 **0.6초 안에 0**이 됨. 곧바로 중지하면 빈 `stopped` 답변. 남의 진행 중인 답변은 멈출 수 없음(404). 중지 뒤 같은 세션에 바로 다시 질문 가능.
- **Hermes가 꺼져 있으면 "서버 오류"가 나가고 아무것도 저장되지 않는다**: 가짜 Hermes가 연결 실패하면 500 `SERVER_ERROR` JSON(SSE 아님), 세션·질문 0개. 실제 서버로도 확인: 닫힌 포트를 가리키는 두 번째 서버에서 500 JSON, 저장된 세션 0, 질문 0, 실제 Hermes는 영향 없음.
- 연결이 끊겨도 끝까지 저장: 첫 조각만 받고 끊어도(실제 소켓) 서버가 답변을 끝까지 받아 `completed`로 저장하고, 끊긴 동안 같은 세션 질문은 `SESSION_BUSY`, 끝난 뒤에는 가능. 실제 Hermes로도 1,836자 답변이 끝까지 저장됨.
- 도중 오류: 받은 조각이 있으면 `stopped`로 저장하고 `error` 이벤트, 없으면 저장하지 않음. 답이 하나도 없이 끝나도 오류.
- 요청 검사: 질문 65,536자 초과 `QUESTION_TOO_LONG`, 빈 질문·NUL 문자 `VALIDATION_FAILED`(모두 Hermes 호출 없음, 저장 없음), 정확히 65,536자는 통과, 없는·남의·삭제된·UUID가 아닌 세션 404, 토큰 없음 401, 임시 비밀번호·차단 403.
- 한 세션에 하나만: 진행 중인 세션에 질문하면 409 `SESSION_BUSY`(Hermes 호출 없음), 다른 세션은 동시에 가능, 두 요청이 동시에 검사를 통과해도 하나만 시작됨(5회 반복).
- keepalive 주석 줄, 응답 헤더(`text/event-stream`, `no-cache`, `X-Accel-Buffering: no`) 확인.
- **변이 검사**(각각 적용해 테스트가 실패하는지 확인한 뒤 원복): 맥락을 보내지 않음, 중지한 답변을 완료로 저장, 도중 오류에서 받은 부분을 저장하지 않음, 빈 답변을 오류로 보지 않음, 연결 끊김을 중지로 처리, 남의 답변도 중지 가능, 받은 조각이 없어도 오류에서 빈 답변 저장, 질문 검사 제거, keepalive 제거, 맥락 조회의 소유 확인 제거, 동시 작업 방지 제거. 모두 잡혔다. **처음에 살아남은 것**: 동시 작업 방지의 등록 단계 검사. 요청 처리 앞쪽의 사전 검사가 대부분의 경우를 이미 막기 때문이다. 두 요청이 동시에 사전 검사를 통과하는 경쟁을 만드는 테스트를 추가했고(구현 그대로 5/5 통과, 검사를 빼면 5/5 실패) 그 뒤로 잡힌다.

지적 10건 중 7건 반영, 3건 넘어감(1건은 일부 반영).
- 반영(진짜 결함): 감독 작업이 취소되면(서버가 꺼질 때 등) SSE 읽는 쪽이 끝나지 않고 영원히 keepalive만 받는 문제. 테스트로 재현한 뒤 종료 처리를 `finally`로 옮기고, 감독이 취소되면 Hermes를 읽던 작업도 함께 취소(연결을 닫음). 서버를 끌 때 5초 안에 못 끝난 작업은 취소하고 기다림
- 반영(진짜 결함): `HermesError`가 아닌 예외가 도중에 나면 받은 부분이 버려지던 문제. 취소가 아닌 모든 예외를 도중 오류로 보고 받은 부분을 `stopped`로 저장
- 반영(진짜 결함): Hermes에 연결하는 중에 중지하면 204인데 질문은 500이 되던 문제. 오류가 아니라 빈 `stopped` 답변으로 마무리
- 반영: 검사와 등록 사이에 `await`가 있어 불필요한 DB 읽기가 생기던 순서. 먼저 등록한 뒤 맥락을 읽도록 바꿈(실패하면 등록 해제). 이 과정에서 **남이 진행 중인 세션에 질문하면 BUSY가 아니라 없는 세션(404)**이어야 한다는 빈틈을 발견해 테스트 추가
- 반영(진짜 결함): 질문 시각이 답변이 끝난 시각으로 저장되던 문제. 질문과 새 세션은 질문한 시각(`asked_at`), 답변과 최근 활동은 끝난 시각
- 반영: 가짜 Hermes의 취소 판정이 타이밍에 의존하던 것을 결정적으로 바꿈(`open_chat`의 `finally`에서 끝까지 갔는지로 판정)
- 반영: 이 작업 파일의 리뷰 내역, 상태 갱신
- 넘어감(일부 반영): 응답이 시작되기도 전에 클라이언트가 끊기면 이벤트 큐가 쌓인다는 지적. 쌓이는 양이 답변 하나의 크기로 제한되고 작업이 끝나면 사라져서 영향이 작다. 연결 중 끊긴 경우(작업 등록 해제)만 고침
- 넘어감: 요청 본문 크기 제한. 모든 엔드포인트에 걸친 문제라 음성 업로드(#30)와 터널 설정(#34)과 함께 다룸. `CLAUDE.md`의 알려진 한계에 기록
- 넘어감: 맥락 길이 무제한. 이슈가 "길이 한도 규칙은 만들지 않는다"고 명시. 긴 세션에서 모델 한도를 넘으면 Hermes 오류로 500이 되는 위험을 `CLAUDE.md`에 분명히 적음
- 넘어감: `httpx.HTTPError` 밖의 전송 예외 래핑. 위의 "모든 예외를 도중 오류로" 수정으로 그런 예외도 받은 부분을 저장하며 `error`로 끝나고, 연결 전 실패는 500으로 처리됨
